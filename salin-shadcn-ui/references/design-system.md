# shadcn 设计系统

## 三层结构

1. **Primitive tokens**：原始颜色、尺寸和字体资源；通常不直接用于业务组件。
2. **Semantic tokens**：`background`、`foreground`、`card`、`primary`、`secondary`、`muted`、`accent`、`destructive`、`border`、`input`、`ring`、`chart-*`、`sidebar-*`。
3. **Component/feature tokens**：只在稳定、跨页面复用的组件语义出现时添加。

以下三层结构适用于 `cssVariables: true` 或项目已有 token 层的情况。若 `components.json` 使用 `cssVariables: false`，普通组件任务保持内联 utility 模式，不擅自切换；只有用户明确要求主题迁移时，才评估删除/重装组件、差异审查和回滚成本。

在 token 模式中优先调整 semantic tokens，再修改组件；不要逐个页面替换颜色。

## 亮暗主题

- 每个前景/背景角色成对定义，不通过简单反相生成暗色。
- 保持颜色模型一致；新项目可选 OKLCH，已有项目沿用其模型。
- 检查正文 4.5:1、大文本与关键界面 3:1、focus ring 3:1 的对比度目标。
- 图表、告警、成功和危险状态不能只靠色相区分。
- 测试系统主题、手动切换、初次加载和服务端渲染，避免闪烁/hydration 问题。

## 圆角、阴影与密度

- 以根 `--radius` 和明确的层级关系控制圆角，避免每个组件自创数值。
- 容器、控件和浮层的圆角可有层级，但不应普遍做成超大胶囊。
- 阴影表达层级；普通静态卡片优先边界、背景差或留白，不同时堆重边框和宽阴影。
- 密度按产品任务决定：运营后台更紧凑，消费页面更宽松；同类控件保持一致高度。

## 组件变体

新增 variant 的条件：

- 有稳定语义名称，而不是“blue”“big”之类视觉名称。
- 至少在多处场景复用，且状态行为一致。
- 不破坏已有默认值、size、disabled、focus 和组合 API。

产品特定的“促销按钮”“AI 生成卡片”等留在 feature 组件，不污染通用 Button/Card。

## 迁移策略

迁移前先确认用户确实要求迁移主题模式或视觉系统。`cssVariables: false → true` 不是普通颜色微调，应按当前官方 CLI/文档核对重装影响并准备回滚。

1. 盘点硬编码颜色、间距、圆角和阴影。
2. 建立语义映射和亮暗对照。
3. 先迁移高频基础组件，再迁移业务组合。
4. 用真实页面逐步回归，避免一次全局替换造成不可控视觉变化。
