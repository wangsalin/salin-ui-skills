# 01 · 需求定义（brief）

AI 搭页面翻车，第一因不是审美，是"不知道这页要解决什么"。本步把一句话需求翻译成 `_workbench/spec.md`：每个区块必须对应一个用户问题。spec 是后续所有步骤的唯一需求源。

输入：`references/00-project.md` 的项目分析（业务目标/用户旅程/功能清单/信息架构）。单页需求必须能对应到 project.md 里的功能项和旅程步骤，对应不上先回第 0 步。

蒸馏自 @西瓜同学🍉 第18集 /finesse-brief。

# 00 · 项目与需求（spec）

第 0 步：一次输出，一次确认。默认轻量 Spec；宏观项目先走 `00-project.md`。

## 北极星（≤5 行，硬约束，写在 Spec 最顶部）
- 业务指标：1 条，可衡量（如"视频分享率"）
- 核心用户任务：1 条（如"3 步内找到并分享刚生成的视频"）
- 铁律：后文每个区块必须能回指北极星，回指不上的删。北极星是 Why 和 What 之间的张力锚点，不许写成"提升用户体验"这类套话。

## 流程
1. **定北极星**：先写业务指标 + 核心用户任务，不超过 5 行。
2. **收需求**：只收一句话——"做什么 + 给谁看"。不写细节、不聊风格。
3. **拆问题**：翻译成用户带着哪几个问题来这个页面（如：参加什么 / 有多难 / 到哪了）。
4. **定区块**：每个问题对应一个区块：区块名 → 用户问题 → 内容要点 → 优先级（P0 必有 / P1 重要 / P2 可砍）。
5. **业务命名统一**：功能/字段/按钮/状态的叫法一次定死（如"作品"不叫"视频"），输出命名表。设计术语（英文映射）不归本步，延后到组件/动效。
6. **写 spec**：输出 `_workbench/spec.md`，含"不做清单"（明确写出这次不解决什么）。
7. **过质量门**：说不出解决哪个问题的区块直接删。宁可页面短，不可区块空。
8. **确认**：输出**决策摘要**（3–5 条会返工的决策 + 默认推荐项），**结束本轮输出等用户回话**。用户回"继续"即按默认走；信息架构级分歧硬停等明确答复。

## spec 必备字段
- 北极星（业务指标 / 核心用户任务，≤5 行）
- 页面一句话目标 / 目标用户
- 区块表（区块 | 用户问题 | 内容要点 | 优先级）
- 业务命名表（名称 | 大白话含义）
- 不做清单
- 一句话"页面定义摘要"（纯文本，给后续步骤当输入用）

## 铁律
- 区块与用户问题严格 1:1：一个区块回答两个问题就拆；一个问题没人回答就补区块。
- 本步不做视觉判断、不定风格、不写交互细节——越界即错。
