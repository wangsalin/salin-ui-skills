# 设计批评

批评回答“为什么这个体验不成立”，不是机械查违例。审查规则和设计判断独立进行，最后合并证据。

## 体验启发式

从以下问题检查核心路径：

1. 系统状态是否可见，用户知道正在发生什么。
2. 术语和流程是否符合用户心智，而非内部结构。
3. 是否有取消、返回、撤销和错误恢复。
4. 相同概念、动作和视觉信号是否一致。
5. 是否预防错误，而非只在失败后提示。
6. 是否让用户识别而不是记忆隐藏规则。
7. 高频用户是否高效，新用户是否能理解。
8. 界面是否去除无关信息而非追求装饰。
9. 错误是否说明原因、影响和下一步。
10. 帮助是否在需要时可找到且贴近任务。

## 认知负担

- 同一时刻是否要求用户记住超过约 4 个独立决定。
- 重要选项是否被同权重的次要内容淹没。
- 是否一次暴露过多字段、参数、图表或 CTA。
- 页面间是否频繁切换术语、位置或交互方式。
- 是否存在不必要确认、重复输入和无法解释的状态。

## 五种视角

- **首次用户**：能否理解这是什么、下一步做什么。
- **熟练用户**：高频路径是否快速，能否批量或键盘操作。
- **无障碍用户**：屏幕阅读器、键盘、低视力、减少动画能否使用。
- **压力用户**：错误、超时、权限和高风险操作时是否清晰可恢复。
- **移动分心用户**：单手、弱网、软键盘、窄屏下是否仍能完成。

## 视觉批评顺序

1. 眯眼看：主要区域与主操作是否仍突出。
2. 灰度看：层级是否不依赖颜色。
3. 看密度：留白是否服务分组，还是浪费空间。
4. 看节奏：标题、正文、列表、图片和操作是否有可解释变化。
5. 看语义：视觉风格是否来自产品内容，还是流行模板。
6. 看一致性：同级元素是否使用相同字体、间距、边界和行为。

## 输出方式

优先选择 3–5 个结构性问题。每个问题说明“看到什么 → 为什么影响任务 → 根因属于什么 → 建议如何修”。视觉建议要具体到层级、密度、排版、颜色角色、组件或流程，不写“更高级、更现代”这种不可验收表达。
