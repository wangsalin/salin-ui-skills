# 报告模板

保持紧凑，先写结论和高优先级问题。没有内容的章节删除。

```markdown
## 结论
- 目标与检查范围：
- 总体判断：
- 最高风险：
- 已验证环境：
- 未覆盖范围：

## 问题

### [P1] 问题标题
- 位置：`path/to/file.tsx:42`；或 `/route`、390×844、暗色
- 证据/复现：执行什么后看到什么
- 影响：对哪些用户、任务或指标造成什么影响
- 根因：缺 token / 一次性实现 / 概念不一致 / 其他
- 建议：最小可执行修复

## 维度概览
- 任务与流程：0–4 或 N/A / 证据类型与简短依据
- 信息与视觉：0–4 或 N/A / 证据类型与简短依据
- 交互与状态：0–4 或 N/A / 证据类型与简短依据
- 响应式与内容：0–4 或 N/A / 证据类型与简短依据
- 无障碍：0–4 或 N/A / 证据类型与简短依据
- 性能与工程：0–4 或 N/A / 证据类型与简短依据

## 验证记录
- 代码与文档：
- 浏览器路径与视口：
- 运行命令：
- 未验证与风险：
```

## 书写要求

- 标题描述问题，不写“建议优化”。
- 每个问题只讲一个根因；重复表现合并说明影响范围。
- 使用真实文件行号、路由、视口和复现步骤。
- 不写无法观察的结果，例如“用户一定会流失”。可写“增加找到主操作的成本”。
- 建议说明改哪里、改成什么、如何验收；不要只写“提升高级感”。
- 只读审查不包含“已修复”；修复任务把修改与验证单列。
