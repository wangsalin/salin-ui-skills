# Salin UI Layout · 页面/APP 布局

## Purpose
回答"这个页面骨架怎么搭"和"这个页面的布局怎么拆"：14 种常用布局模式的分区、栅格、红线，外加一套看图拆布局的分析框架。

## Workflow A — 定骨架（新页面）
1. 先定端（App/Web）与页面类型（首页/列表/详情/表单/营销页/工作台…）。
2. 跑检索：`python scripts/search.py "<页面类型+业务>" --full`，读分区与栅格。
3. 按分区从上到下排布，先定骨架再填组件（组件查 `salin-ui-components`，动效查 `salin-ui-motion`）。
4. 对照红线自查一遍，命中的当场改。

## Workflow B — 拆布局（分析现有页面/App）
输入：截图、链接或文字描述。输出布局拆解报告，固定六段式：
1. **布局模式命名**：命中库中模式则具名（如"信息流+底部Tab"），无命中则用"X+Y 混合"描述，不硬套。
2. **分区拆解**：按视觉顺序列出所有区域（一级分区），注明每个区域的内容与占比。
3. **栅格与间距**：列数/边距/卡片间距/圆角，量不到的写"目测约"，不编精确值。
4. **信息层级**：一级信息（首屏核心）/ 二级（支撑）/ 三级（弱化），指出层级是否清晰。
5. **导航模式**：底部Tab/顶栏/侧边栏/抽屉，评价跳转成本。
6. **评价**：可借鉴点（对照库中模式的优点）+ 问题点（对照红线），每条一句话。

## Query Contract
- 查询词 2–4 个：页面类型 + 业务，如"电商 商品列表""SaaS 工作台""社交 信息流"。
- 分析类任务直接走 Workflow B，不需要先检索。
- 看不清/量不到的不编，标注"需确认"。

## Operating Rules
1. 先骨架后组件：布局阶段不讨论按钮颜色，只讨论分区与层级。
2. 分区必须写占比或顺序，不许"大概分几块"。
3. 每个新页面交付时必须回答：用的哪个布局模式、改了哪里、为什么改。
4. 拆布局报告里"问题点"必须对照库中红线逐条过，不许凭感觉批评。
5. 加新布局 = 在 `data/layouts.csv` 加一行（字段对齐表头），不许改脚本结构。
